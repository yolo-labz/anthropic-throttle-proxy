# OpenCode free-tier limits — vendor facts + measured safe envelope

## 0. What this slice answers

1. What does opencode.ai actually publish about the free tier on the two
   inference gateways (concurrency caps, per-model budgets, 429 vs soft throttle)?
2. What does this host *measurably* hit on those gates (journal + live health)?
3. What is the **safe operating envelope** — maximum parallel width and request
   rate — at which we do not trigger the limit?

Evidence discipline used throughout: every claim is tagged **[M] measured**
(reproduced receipt shown), **[D] documented** (vendor docs, URL + fetch receipt),
or **[H] hypothesis** (mechanism consistent with the data but not proven).
Nothing tagged [H] may be treated as a fact by a downstream slice.

## 2. Vendor-documented facts (S1–S4)

### 2.1 The two products are different machines

**[D]** Go (S1) is a subscription: **$10/mo "Go"** and **$40/mo "Go Plus"** —
*not* the `$15` / `$60` pair recorded in the community snapshot of 15/10 (S10,
`opencode-zen-offers-2026-10.md`). Zen (S3) is
pay-as-you-go credits ("You are charged per request and can add credits to your account").

### 2.2 Go usage limits are a **rolling dollar ladder per model**, not a concurrency cap

**[D]** S1, section "Usage limits":

> Usage limits are defined as monthly dollar amounts. […] Each model has the
> following usage limits: **5-hour — 20% of the monthly limit; weekly — 50%;
> and monthly — 100%**. […] Token pricing is the same for Go and Go Plus.

**[D]** The free models in that table carry the value **`Unlimited`** in the
"Monthly limit" column, and `Free` in every token-price column:

| Free model on Go (S1) | Input | Output | Cached read | Monthly limit |
|---|---|---|---|---|
| LongCat 2.5 Preview Free *(limited time)* | Free | Free | Free | Unlimited |
| Beam Free *(limited time, limited regions)* | Free | Free | Free | Unlimited |
| MiniMax M3.1 Flash Free *(limited time)* | Free | Free | Free | Unlimited |

The "limited time" / "limited regions" tags are vendor-published and matter for
fleet planning: any of these ids can disappear without a deprecation notice.

### 2.3 Free models are **excluded** from Console budgets — and budgets 429

**[D]** S2, "What counts":

| Spend | Counts toward budgets |
|---|---|
| Paid Console models | Yes |
| Models on your own providers with a price set | Yes |
| Web search | Yes |
| **Free models** | **No** |
| **Go usage within the plan** | **No** |
| Go extra usage paid from credits | Yes |

**[D]** S2, "When a budget is reached":

> New requests fail with **HTTP 429** until the budget resets or an admin raises
> it. The response does not say which budget was reached.
> `Upstream request failed: Account budget exceeded`
> Budgets are checked when a request starts. Requests already in progress finish.

Two consequences for us, both **[D]**: (a) a Console-budget 429 is a
**monthly** condition (budgets reset the 1st at 00:00 UTC), and (b) it can
never be the cause of a free-model 429, because free models do not count.
S2 also states budgets are per workspace + per member/service-account, and that
"$0 budget blocks all spend that counts toward budgets".

### 2.4 The client contract on Go is explicit — and we violate one clause

**[D]** S1, "Where can I use it?":

> OpenCode Go is designed for OpenCode and other coding agents that produce
> similar types of requests. **Traffic is monitored for abuse** that degrades the
> experience for other users.
> Your client should:
> * Send typical coding agent traffic
> * Identify itself with its own user agent, such as `my-coding-agent/1.0`,
>   rather than a generic SDK or HTTP-library name.
> * Send a **stable session ID in `x-opencode-session` for each conversation**
>   so we can optimize routing and prompt caching.

**[D]** S1 also publishes a **validated-clients** table. It lists Claude Code,
Codex, ZCode, jcode, Kilo Code CLI, Hermes — and **Pi** ("Current builds send
session information for OpenCode. Update older installations."), plus a
"known problematic" table (DeepSeek Harness, GitHub Copilot Chat, Kimi Code,
MiMo Code) tracked by issue numbers. So third-party clients are a *documented,
expected* traffic class, not a blocked one — **but only while they behave like
a coding agent and keep the session header contract.**

**[M]** Gap on this host: `~/NixOS/modules/home/opencode.nix:1339-1341` pins
**one** UUID for every request the host makes:

```nix
headers = {
  # Routing key, not a secret — same stable id pi installs send.
  "x-opencode-session" = "ab537723-bd19-4cb1-8393-a9e1e475eaf4";
};
```

The gateway forwards client headers verbatim (`forwarding.py:304` drops only
`HOP_HEADERS` and provenance headers), so every pi pane, every herdr tab and
every parallel turn on this desktop presents **the same session id**. The
documented contract is *per conversation*. **[H]** One id shared by ~30
concurrent turns both defeats the prompt-caching the header exists for and
removes the routing signal opencode uses to tell "one agent, many turns" from
"one key, many tenants" — a plausible contributor to the free-lane 429s in §4.
Not proven: no upstream statement links the two.

### 2.5 There is no published free-tier rate limit

**[D]** Neither S1, S2, S3 nor S4 states a requests/min, tokens/min or
concurrency number for free models. Zen's model page (S3) is purely a
price + endpoint table. Go's (S1) is a *dollar* ladder. **The number does not
exist in the public docs — it is discovered only by hitting it.** That is the
single most important vendor fact for this mission: "maximum parallel width
without triggering the limit" cannot be satisfied by reading a spec sheet.

### 2.6 Catalog drift (models.dev ≠ upstream)

**[M]** The generated catalog (S5) emits **84 zen** models of which **9 free**,
and **29 go** models of which **2 free** (`beam-free`, `longcat-2.5-preview-free`).
The upstream go gateway nevertheless served `minimax-m3.1-flash-free` (200,
19/10 18:46:41), which is in the vendor docs (S1) but absent from the generated
nix. The generator's own filter (`tool_call && status != "deprecated"`,
`gen-pi-opencode-models.py`) is stricter than the upstream catalog. Net: **the
go free set is 3 models, our catalog shows 2.**

## 3. The two upstream 429 signatures are different machines

**[M]** This is the most operationally useful measurement in the slice. The two
gates do not get the *same* 429.

### 3.1 Go gate — **bare 429 after a ~49 s hold**, free-model specific

**[M]** 18 × `done … status=429` on the go gate 19/10 16:47:50 → 18:53:48, and
**every one is `model=longcat-2.5-preview-free`**. Pushback lines carry
`retry_after=0.0 synthetic_pause=True` — i.e. **no `Retry-After` header at all**:

```
Oct 19 16:47:10 … rate-pushback-retry bid=e574f38a status=429 retry=1/1 pause=30.0 retry_after=0.0 synthetic_pause=True
Oct 19 16:47:10 … aimd-shrink bid=e574f38a status=429 max_concurrent=44 retry_after=0.0 pause=30.0 synthetic_pause=True (budget/real-retry-after pushback)
Oct 19 16:47:50 … done … status=429 … model=longcat-2.5-preview-free elapsed_ms=48957 inflight=2 queued=0 served=522
```

**[M]** The upstream holds the request and *then* refuses. Elapsed time on the
18 surfaced 429s: **min 36.2 s, median 48.7 s, max 50.7 s**. (Compare: the
successful free requests in the same window had median 9.6 s.)

**[M]** It is **not** a concurrency gate. Those 429s were served at
`inflight` 0–2, and the same AIMD ceiling that produced them had been running
free of any 429 at far higher widths earlier the same day.

**[M]** It is **not** an account/plan budget gate. In 9 of the 10 minutes that
contained a go 429, a **paid** Go model returned 200 in that same minute
(`paid200` 1–3, `free200` 0). A budget gate (S2) would do the opposite: it
never blocks free models and it does block metered ones.

### 3.2 Zen gate — **429 with a real, multi-hour `Retry-After`**, plus an intermittent 403 client-lock

**[M]** 4 × `done … status=429` on the zen gate, all free models, all with a
real upstream `Retry-After` (`synthetic_pause=False`):

| Time | Model | Retry-After | ≈ reset |
|---|---|---|---|
| 18:27:09 | `mimo-v2.6-flash-free` | 9171 s | +2 h 33 m |
| 18:27:10 | `mimo-v2.6-flash-free` | 9171 s | +2 h 33 m |
| 18:27:10 | `mimo-v2.6-flash-free` | 9170 s | +2 h 33 m |
| 18:57:20 | `glm-5.3-flash-free` | 7361 s | +2 h 03 m |

The live limiter snapshot (S8, 19:40 BRT) still latches it:
`"last_ratelimit": {"retry-after": "7361"}`, `retry_after_until` ≈ +2 h from
the event, `retry_probe_required: true`.

**[M]** Zen additionally answers an **intermittent 403 client-lock** on free
models (16 `credential-reject` events on 19/10, 15 of them before 18:27, plus
7 × HTTP 400 from the same upstream):

```
Oct 19 12:48:38 … credential-reject bid=e574f38a status=403 streak=1/3 detail="OpenCode's free tier can only be used from within OpenCode. Download it at https://opencode.ai and keep building."
```

It is intermittent, not deterministic — 767 free requests returned 200 on the
same credential the same day — and the gateway's 3-strike streak logic
(`credential-dead` → `credential-recovered`) is what keeps a lane alive through
it. This is the same wall the 15/10 community sweep recorded (S10).

### 3.3 What the client binary already knows about opencode's error classes

**[M]** `opencode` v2.0.32 (S9) contains the upstream error-code set
`{"insufficient_quota","usage_not_included","billing_error","gousagelimiterror","freeusagelimiterror","creditlimitexceeded"}` —
so `GoUsageLimitError` and `FreeUsageLimitError` are **distinct upstream error
types**. The free tier has its own limit object, separate from the Go plan's.
(No message text is recoverable from the bundle; only the code names.)

### 4.1 The free lane is *lossy by design* at our target rate

**[M]** Bare-429 absorption is already the norm, not an anomaly:

| Gate | surfaced 429 (`done status=429`) | gateway pushbacks (`rate-pushback-retry`) | absorbed by the in-gate retry | ratio |
|---|---|---|---|---|
| go | 18 | 43 | 25 | **58 % never reach the client** |
| zen | 4 | 4 | 0 | 0 % (its 429 carries a 2.5 h `Retry-After`, so the single retry is pointless and gets fast-failed) |

Free-model 429 density on go: **1 × 429 per 32 successes**. Zen: 1 per 192.
That is a 1–3 % per-request loss rate under load — **[H]** consistent with a
shared capacity pool being momentarily full, not with anyone's usage budget
being exhausted (which would be total and would last the window).

### 4.2 The 429 is not what killed the panes — the AIMD reaction is

**[M]** `src/anthropic_throttle_proxy/config.py:151-262` makes every 429 a
congestion signal:

```
AIMD_STATUSES = {429, 503}          # config.py:262
AIMD_DECREASE  = 0.7                # config.py:260  (multiplicative)
AIMD_RAMP_AFTER = 10 / _FAST = 5    # config.py:233/245 (additive)
AIMD_BACKOFF_S = 30                 # config.py:155
```

All journal windows in §4 are 19/10 only — `journalctl` for these two units
retains nothing before 07:56 today, so every number here is a single-day
measurement, not a multi-day average.

**[M]** 18 bare 429s over 2 h produced **55 `aimd-shrink` events** and moved the
ceiling **64 → 44 → 30 → 21 → 14 → 9 → 6 → 4 → 2 → 1** in 5 minutes, then held
it at 1–2 for **2 h 30 m** (16:52 → 19:18). At that width the queue could no
longer drain 171–303 s generations:

```
Oct 19 19:02:30 … queue-wait-timeout … reason=pre-queue-depth max_wait_s=179.984 inflight=1
     queued_total=1 max_concurrent=1 service_s=177.605 source=inflight est_wait_s=355.21 retry_after_s=300
```

i.e. `est_wait 355 s > max_wait 180 s` → 503 → the pi retry burn-loop that
produced most of the incident's 46 `client-disconnect` events (33 of them inside
this window). **Building the ceiling to 64 took 52 additive grow events spread
over 5 h; destroying it took 5 multiplicative shrinks inside 5 minutes.** The
asymmetry, not the vendor, is what put the fleet at width 1.

**[M]** The repo already contains the right concept and did not apply it here.
`config.py:268-279`:

```
OVERLOAD_STATUSES = {529}
# 529 = upstream OVERLOADED (capacity, NOT your usage). We honor any
# retry-after and count it separately, but do NOT shrink the ceiling —
# shrinking would throttle you for someone else's capacity problem.
```

and `config.py:158-164` records the *same* historical failure mode for Anthropic:

> Anthropic returns 429-with-no-Retry-After for BOTH: a 5h/7d budget
> soft-throttle AND a per-account concurrency/requests-per-minute cap. … a
> full 30 s pause just collapses the active account to cap=1 and holds it there
> under fleet load (03/07/2026 single-active concentration incident).

**[H]** The opencode free-lane bare 429 is the third member of that taxonomy —
a headerless, non-concurrency, non-budget capacity refusal — and belongs with
`OVERLOAD_STATUSES` ("don't shrink"), not in `AIMD_STATUSES`.

**[M]** A sibling slice is already wiring this: `src/anthropic_throttle_proxy/
free_budget.py` (declared `THROTTLE_FREE_BUDGETS` allowance + upstream-wall
latching, refusing locally so no AIMD signal is minted), plus
`specs/334-queue-admission/` (`aimd_owned` / `no aimd shrink` provenance in
`limiter.py`, `proxy.py:4007`), `specs/333-free-gate-spillover/`,
`specs/334-pi-client-alignment/` and the `free-gate-watchdog` observability
slice. This document is their vendor-side input; it deliberately does not
duplicate their design work.

## 5. Safe operating envelope (the deliverable)

### 5.1 Numbers we can defend today

| Knob | go `:8770` | zen `:8774` | Evidence |
|---|---|---|---|
| **Sustained parallel width (free models)** | **16** (measured clean at 15–17 inflight for 12 min) | **16** (measured clean at 14–18 inflight for hours) | §4 post-recovery table; zen clean window |
| **Max width ever observed clean** | 33 (AIMD ceiling) / 17 (real inflight) | 18 (real inflight) | §4 |
| **Do NOT assume** | 64 is safe for free models — that width was clean on a **paid** mix only | — | §4, 11:38–16:42 window |
| **Sustained request rate (free)** | **≈ 34 free req/min** sustained clean | **≈ 40 req/min** short bursts clean | §4 |
| **Expected loss at that rate** | ~1 bare 429 per 32 successes (≈3 %) | ~1 per 192 (0.5 %), then a 2.5 h wall | §4.1 |
| **Quota horizon** | unknown — no wall observed on the go gate during 19/10 (bearer live 11:31 → 19:44) | **~750–780 free requests then a 2.0–2.6 h `Retry-After`** | §3.2, §4 |
| **Warm-start ceiling (`THROTTLE_AIMD_INITIAL_CONCURRENT`)** | 12 (live) — keep | 12 (live) — keep | unit env |
| **`THROTTLE_AIMD_MIN`** | 2 (live) — **not sufficient**; the lane still died at 1–2 | 2 (live) | §4.2 |
| **`THROTTLE_MAX_HOLD_RETRY_AFTER_S`** | 240 (live) — correct | 240 (live) — **mandatory**: zen's 2.5 h retry-after must be fast-failed, not held | `config.py:290-296`; §3.2 |
| **`THROTTLE_QUEUE_MAX_WAIT_S`** | 180 (live) < pi idle 300 — correct | 180 (live) | unit env; incident |

**Net answer to "maximum parallel width":** with today's gate behaviour the
fleet can safely hold **16 in-flight free requests per gate** and sustain
**~34–40 free requests/min per gate**. Widening beyond that does not buy
throughput today — the lossy 429 plus the 0.7 shrink factor will pull the
ceiling back down — and the *measured* evidence for anything above 18 in-flight
free is a single 12-minute window at 17.

### 5.2 What would actually buy more width (ordered)

1. **Stop treating the free-lane bare 429 as congestion.** 58 % of them are
   already absorbed silently; absorbing 100 % with a bounded retry budget keeps
   the ceiling where it is. Owner: `specs/334-queue-admission/` +
   `free_budget.py`. **This is the highest-leverage change by a wide margin.**
2. **Circuit-break on the *Retry-After* class, not on the shared lane.** A zen
   429 with `retry-after ≥ 3600` means "this model, for ~2 h" — route around
   the model; do not shrink the semaphore shared by the other 8 free ids.
3. **Respect the `x-opencode-session`-per-conversation contract** (S1 §2.4).
   One UUID per pane/session instead of one per host (S6). Zero risk class:
   it is what the vendor asks for and it restores prompt caching. Owner:
   `specs/334-pi-client-alignment/` territory, NixOS side.
4. **Free the catalog from models.dev drift** — Go's free set is 3 ids, the
   generated nix has 2 (`minimax-m3.1-flash-free` served 200 today). S5's
   `gen-pi-opencode-models.py` filter needs the upstream-vs-models.dev delta.
5. **Do not chase width by raising `AIMD_INITIAL_CONCURRENT`.** The ceiling is
   discovered by AIMD in ~40 additive steps anyway; a higher warm start only
   raises the height it falls from.

### 5.3 Things we must *not* conclude

* **[H]** that opencode has a hidden concurrency cap of 12/16/32. No such
  number is documented (§2.5) and 33 was reached clean on the go gate.
* **[H]** that the bare go 429 is a daily quota. It interleaved with 158
  successes on the same model inside the same window (§3.1) — a daily quota
  would be solid for its whole window.
* **[H]** that adding more opencode keys multiplies the free width. The Zen
  offers note (S10) and MiMo's own scope test (`1. Projects/Anthropic-Throttle-Fleet/MiMo API rate limit — scope test…md`)
  both suggest opencode-style limits are per-account, not per-key. **Not tested
  on opencode — do not assert it.**
* **[H]** that the client-lock 403 on zen is deterministic. Measured opposite:
  767 successes and 16 rejects on the same credential, same day (§3.2).

## 7. One-line summary for the integrator

> The free gateways have **no published concurrency cap**; what they have is a
> **lossy, headerless 429 on the go lane (~1 per 32 successes at our target
> rate, arriving after a ~49 s hold) and a 2–2.6 h `Retry-After` wall on the zen
> lane (~750 requests apart)**. Both are per-request/window events, not
> congestion — and the fleet's AIMD currently reads both as congestion, which
> is what collapsed `:8770` to `max_concurrent=1` for 2 h 30 m today. Safe
> width **16 in-flight free per gate**, safe rate **~34–40 free req/min per
> gate**; the throughput win is in *not shrinking*, not in widening.
