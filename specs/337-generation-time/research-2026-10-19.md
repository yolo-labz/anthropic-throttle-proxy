# R3 — Where the 171–303 s generation time actually goes

Research slice, 19/10/2026. Branch `337-generation-time`. This file is the only
thing this branch commits.

**Question.** The 19/10 incident collapsed because free-model generations ran
171–303 s against a 180 s client wait budget. When `R > max_wait` the queue
admits nobody at any concurrency width (`docs/AIMD-POLICY-FREE-LANES.md` §2).
Where does the time go, and what cuts it without losing output quality?

**One-line answer.** It is *all* upstream generation — 95.5 % of arrivals got a
slot in under 1 s and the client↔gate delta is +0.4…+1.5 s at p50 — and it is
**decode-bound, not prompt-bound** (OLS on the payg lane: 82 % of turn-time
variance is explained by output-token count alone; prefill+TTFT is a 7.7–9.6 s
intercept). Every prompt-side shrinker in the stack therefore has a hard ceiling
of ~10–18 % on median turn time and ≈0 % on the >180 s tail. `body_shrink` is
dead code on these lanes. `pi-context-lean` is live and removes 23.5 % of
message bytes, but it is trimming the wrong term.

## 2. Queue wait vs upstream service time — the gap is ~zero

The ledger's `turn_ms` is wall clock; the gate's `elapsed_ms` is upstream
service time. Joined on same model, gate `done` within ±2 s of `turn_end`:

| model | pairs | turn p50 | gate p50 | delta p50 | delta p90 |
|---|---:|---:|---:|---:|---:|
| `mimo-v2.6-flash` | 786 | 18.7 s | 13.2 s | **+0.4 s** | +27.8 s |
| `mimo-v2.6-flash-free` | 785 | 16.2 s | 11.8 s | **+0.8 s** | +37.4 s |
| `longcat-2.5-preview-free` | 546 | 8.7 s | 5.8 s | **+1.5 s** | +28.1 s |

The p90 tail on the delta is an artifact of the ±2 s join under concurrency
(a turn can be paired with a sibling request); the p50 is the honest number.

Measured directly at the gate, arrival (`queue+`) → dispatch (`start`), same
`cid`:

```
dispatches with a matched arrival: 3266/3266
same-second (queue wait < 1s): 3120 = 95.5%
wait: p50=0s p90=0s p99=32s max=139s
```

`p99 = 32 s` is the 180 s wait budget being spent, and it is exactly the
`QUEUE_MAX_WAIT_S=180` regime the AIMD doc describes — but it is a 4.5 %
minority. **The other 95.5 % of a turn's wall clock is upstream decoding.**

Corroborating: `inflight` at dispatch was p50=10, p90=15, p99=17, max=18, all
day, against a configured `max_concurrent=1024`. The semaphore was never the
binding constraint in the healthy regime.

## 4. `body_shrink` is dead code on the free lanes

`src/anthropic_throttle_proxy/body_shrink.py` shrinks `tool_result` and
`image` blocks, but **only above a 28 MiB soft cap and only on
`/v1/messages`**:

```python
# body_shrink.py:180
if "v1/messages" not in path:
    return body, {"trimmed": False, "reason": "non-messages-path", ...}
if original_bytes <= CAP_BYTES:          # CAP_BYTES = 28 MiB default
    return body, {"trimmed": False, "original_bytes": original_bytes}
```

Call site: `_shrink_forward_body` (`proxy.py:4796`) → `_apply_body_shrink`
(`:4537`) → `shrink_body`. It runs on every POST, but:

* **Path.** 100 % of go-gate traffic is `/openai/v1/chat/completions`
  (7 201 of 7 201 non-health requests in the day's journal). zen-gate is
  2 837 `/openai/v1/chat/completions` + 18 `/v1/chat/completions`. None match
  `"v1/messages"`.
* **Size.** The largest prompt observed today was `in + cache_read` ≈ 137 478
  tokens (in=838, cache_read=136 640) ≈ 0.55 MB, ~50× under the 28 MiB cap.

So `body_shrink` cannot be the answer, and raising/lowering its knobs changes
nothing on these lanes. It is an Anthropic-32 MB-cap insurance policy for the
paid lane (`:8765`), correctly scoped and correctly inert here. Verified by the
absence of any `body_shrink` or even `body_passthrough` line in both free-gate
journals for the whole day.

## 5. `pi-context-lean` — live, provider-agnostic, and trimming the wrong term

`~/.pi/agent/extensions/pi-context-lean.ts` (120 lines) thins the **request**
only: drops `thinking` blocks signed `reasoning_content` on assistant turns
older than the newest 4, and caps text blocks of tool results older than 2
assistant turns at 4 000 chars. The transcript is untouched.

**Coverage.** The marker string `…[context-lean: output bounded]` appears in
this very session's own tool output 20 times, and this session is
`PI_PROVIDER=opencode-go / PI_MODEL=mimo-v2.6-flash`. So it is applied to the
opencode providers, not just some. Across all 307 session files touched today,
18 files (5.9 %) carry the marker. **That 5.9 % is not a coverage figure** — the
marker is only emitted when a tool result is actually bounded, and
`reasoning_content` thinking drops emit no marker at all (the code has no notice
for them). Absence of the marker therefore says nothing about whether the
extension ran; only its presence is informative.

**Byte reduction (replayed offline).** I re-implemented the exact algorithm
(`KEEP_TURNS=4`, `TOOL_RESULT_LIMIT=4000`, `OLDER_THAN=2`) in Python and
replayed it over the message arrays of all 246 touched sessions that had ≥6
messages:

| class | n | message bytes | removed | % |
|---|---:|---:|---:|---:|
| sessions with `reasoning_content` thinking | 184 | 628.8 MB | 162.6 MB | **25.9 %** |
| sessions tool-result-only | 55 | 253.6 MB | 44.5 MB | **17.6 %** |
| nothing trimmable | 7 | 0.0 MB | 0.0 MB | — |
| **TOTAL** | **246** | **882.4 MB** | **207.1 MB** | **23.5 %** |

Per-session reduction: median **39.1 %**, p90 57.1 %, max 73.0 %.

**But this is the wrong lever for generation time.** Section 3 puts the whole
prefill+TTFT cost at 7.7–18.1 s of a turn that runs 20–200 s. Cutting 24–39 %
off a prompt that is already mostly `cache_read` (p50 51 072 tokens on turns
under 60 s) buys single-digit seconds at the median and **nothing** on the
>180 s tail, which is 16/23 decode-bound with `cache_read` p50 96 768. The
extension is worth keeping — it is cheap and it reduces billed input — but it
is not the 503-storm lever, and nobody should spend a slice raising its
constants expecting a latency win.

## 6. Streaming: the gate samples completion, not first token

Traced end to end:

1. `limiter.slot()` is an `async with` (`limiter.py:1546-1570`); `__aexit__`
   calls `limiter.release(...)`.
2. `release` → `_note_completion` appends the sample
   (`limiter.py:911`): `samples.append(max(0.0, time.monotonic() - held[1]))`
   where `held[1]` is the dispatch stamp. That is **dispatch → slot release**.
3. The slot is held across `_forward_with_retry` → `_forward_once_into_sse`
   (`proxy.py:2773`), which pipes the *entire* upstream body into the client
   SSE stream. So the slot is released at **stream EOF**.

`_service_estimate` (`limiter.py:426`) then takes the p90 of those samples
(`_SERVICE_QUANTILE = 0.9`, `limiter.py:33`) plus, as a conservative floor, the
age of the oldest currently-held slot (`source=inflight`).

**All 16 `queue-wait-timeout` events today carry `source=inflight`** — the
estimator never even used a completion sample during the incident, it used the
"this slot has already been held for N seconds" lower bound:

```
17:57:24 pre-queue-depth service_s=182.624 source=inflight est_wait_s=182.624
19:02:26 pre-queue-depth service_s=173.535 source=inflight est_wait_s=347.07
19:02:30 pre-queue-depth service_s=177.605 source=inflight est_wait_s=355.21
19:03:03 pre-queue-depth service_s=210.241 source=inflight est_wait_s=210.241
```

`est_wait_s=347.07` against `max_wait_s=179.991` — that is the 503 storm,
arithmetically identical to `AIMD-POLICY-FREE-LANES.md` §2 row "floor=1,
ahead=1, R=200 → 503", with `max_concurrent=1` on every one of the 16 lines.

### What first-token-first admission would buy

If the slot were released at first token instead of at EOF, the estimator's `R`
would drop from the measured p90 (90–140 s) to the measured prefill+TTFT
intercept (7.7–18.1 s). Re-running §2's arithmetic at the incident values
(`floor=1`, `ahead=1`, `R`→8 s):

| | R (completion) | R (first-token) |
|---|---:|---:|
| est_wait, ahead=1, floor=1 | 347 s | **16 s** |
| vs `max_wait` 180 s | 503 (rejected) | admitted |
| depth absorbable per generation (`max_wait / R`) | **< 1** | **22** |

So the admission arithmetic flips hard: at `R=8 s` even a floor of 1 absorbs 22
queued arrivals. **This is a genuine width lever, and it costs zero output
quality** — the bytes on the wire are unchanged, only the accounting moves.

### But there is a measured counter-argument, and it is not a guess

The go gate received **34 `aimd-shrink … status=429 max_concurrent=1`** events
between 16:52:28 and 18:57:24 — 2 h 5 min of sustained 429 pushback **while
already at concurrency 1**. Full shrink ladder observed today:

```
16:47:10 mc=44 → 16:47:50 mc=30 → 16:48:29 mc=21 → 16:49:09 mc=14
16:49:49 mc=9  → 16:50:28 mc=6  → 16:51:09 mc=4  → 16:51:49 mc=2  → 16:52:28 mc=1
… 34 shrinks at mc=1 …
18:49:02 mc=8 → 18:50:24 mc=5 → 18:51:44 mc=3 → 18:53:15 mc=2 → 18:53:48 mc=1
```

A lane that keeps 429ing at concurrency 1 is not concurrency-limited. **Inference
(marked as such):** the free tier's 429 is substantially *per-window /
per-account-requests*, not *per-inflight*. If so, releasing slots at first token
raises true upstream concurrency without raising the sustainable request rate,
and the extra admissions convert into more 429 churn rather than more served
turns. **This needs one measurement to settle, and that measurement does not
exist yet:** a concurrency sweep on a free model holding total request rate
constant (e.g. 1 gen/s at concurrency 1 / 4 / 8 / 16, count 429s per 100). I
did not run it — it spends free-tier budget during a day that was already
429-saturated, and it is a deliberate experiment, not a probe.

## 7. What is actually burning the tail (and what is not)

Total upstream request-seconds today, status 200: **90 175 s (25.05 request-hours)**.

| model | reqs | request-s | share | of which >180 s |
|---|---:|---:|---:|---:|
| `mimo-v2.6-flash` | 1550 | 65 738 | 72.9 % | 12 158 s (18.5 %) |
| `mimo-v2.6-flash-free` | 757 | 16 262 | 18.0 % | 0 s |
| `longcat-2.5-preview-free` | 590 | 8 151 | 9.0 % | 291 s (3.6 %) |

Three distinct sinks, quantified:

1. **Decode of long answers — 18.5 % of the payg lane's request-seconds.**
   16/23 tail turns, out p50 7 480 tokens. Unavoidable without truncating
   output. Out of scope for a "no quality loss" change.
2. **Upstream stalls — 7/23 tail turns plus 8 `SocketTimeoutError`
   mid-stream events in one 2-second burst (19:23:20–22).** These are
   `THROTTLE_UPSTREAM_SOCK_READ_TIMEOUT_S=120` firing: the vendor went silent
   for 120 s and the proxy gave up. Every one of the 15 mid-stream events today
   logs **`response committed, no retry`** — the slot burned, the client got a
   truncated stream, and the whole generation had to be re-issued by the seat
   as a fresh turn. This class is pure waste and is the one part of the tail
   recoverable at *zero* quality cost.
3. **Pushback pauses — 44 synthetic `pause=30.0` = 1 320 s, plus 5 real
   `Retry-After` walls totalling 38 632 s** (9 171 s ×2, 9 170 s, 7 361 s,
   3 759 s). The real walls are not slot time — `free_budget.py` deliberately
   does not reimplement them and `retry-after-fast-fail` (227 events on zen)
   refuses locally before a slot is burned — but they are the reason the lane
   was at `max_concurrent=1` for two hours.

## 8. Ranked recommendations

Ranked by measured bytes-of-wall-clock per unit of risk, and each marked with
what it does *not* fix.

| # | Change | Measured win | Quality cost | Confidence |
|---|---|---|---|---|
| 1 | **Retry the stall class.** On `upstream-mid-stream … SocketTimeoutError` with **zero body bytes written**, re-issue upstream instead of committing a truncated stream. | Recovers ~30 % of the >180 s tail (7/23 turns, ~194 s each) plus 8 events in the 19:23 burst. Free: no new upstream load, it *replaces* a lost generation. | **None** — the alternative today is a seat re-running the turn from scratch. | High (receipts in §7) |
| 2 | **First-token slot release** in `FairBearerLimiter` (release at `_first_chunk_written`, keep a separate throughput meter). | `R` 90–140 s → 7.7–18.1 s; `est_wait` 347 s → ~16 s; depth absorbable `<1` → `22`. Fixes the §2 admission arithmetic outright. | None to the output. But see §6 counter-argument: the lane 429s at concurrency 1, so the *served* width may not follow the *admitted* width. | **Needs the concurrency sweep first.** Do not land this before that measurement. |
| 3 | **Declare `THROTTLE_FREE_BUDGETS`** (module exists, currently inert — the env var is unset on both gates, so `free_budget.py` is default-off). | Converts 44 × 30 s synthetic pauses (1 320 s) and the 16 `queue-wait-timeout` refusals into local `Retry-After` refusals that burn no slot. Does not shorten a single generation. | None | High |
| 4 | Raise `pi-context-lean` constants. | **~0 on generation time.** §3 caps the whole prefill lever at 7.7–18.1 s of a 20–200 s turn. Worth doing for billed input, not for latency. | Small (older tool output re-fetched) | High |
| 5 | Tune `body_shrink`. | **0.** Dead on these lanes by path and by 55× margin on size (§4). | n/a | Certain |

**Explicitly rejected as the "biggest parallel-width lever":** a bigger
semaphore. `max_concurrent` was 1024 all day and actual `inflight` peaked at 18;
the AIMD *floor* (set by 429 pushback, not by config) was the effective width,
and the histogram of inflight-at-dispatch is visibly bimodal — 1 105 of 3 266
dispatches (33.8 %) ran at `inflight ≤ 3`, the shrunk regime, against a healthy
cluster at 9–16.
